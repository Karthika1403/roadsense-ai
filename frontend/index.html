Architecture

From sensor to decision

The same pipeline a connected-bike platform would use, built end to end.

01

Sense

Engine temperature, rpm, battery voltage, vibration, speed and load stream from the bike or the simulator.

02

Validate and store

A FastAPI service checks ranges with Pydantic and saves each reading to PostgreSQL.

03

Model

Anomaly detection, component health scoring and a failure-risk classifier run on every reading.

04

Advise

Rules and model outputs become labelled, prioritised service advice on this dashboard.

StrategyRuleWeakness
ReactiveFix it when it breaksRoadside breakdowns, safety risk, costly repairs
PreventiveService every set km or monthsReplaces healthy parts, still misses early failures
PredictiveService when data shows degradationNeeds sensors, data and models

The basics, by system

What this can and cannot claim

Failures are about 3.4% of AI4I rows, so a model that always predicts “no failure” scores about 96.6% accuracy and is useless. Recall, precision, F1 and PR-AUC are the honest measures. Remaining-life figures here are illustrative.
